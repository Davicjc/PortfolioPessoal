On MikroTik, an OSPF neighbor that drops simply disappears from the table: there is no down state to poll for. The portal keeps a registry of every neighbor it has seen and infers the drop from the absence, guarding against the false positive where an entire PE goes unreachable. It also detects whether RouterOS is v6 or v7, since BFD sits at different API paths.

The problem

On RouterOS, an OSPF neighbor that goes down simply vanishes from the table — there is no “down” state to poll. Generic tools don't notice an absence, so a failed link between PEs only surfaced when someone happened to look at the router.

Decisions

  1. 01

    Infer failure from absence

    The portal remembers every neighbor it has seen and marks it OFFLINE when it disappears — guarding against the false positive where the whole PE becomes unreachable.

  2. 02

    Detect the version automatically

    BFD lives at different API paths on RouterOS v6 and v7. The portal detects the version and queries the right path with zero configuration.

  3. 03

    Alert once per transition

    A background collector runs every 30 s and sends one Telegram message when a neighbor drops and one when it returns, with timestamps and duration — never one per poll.

  4. 04

    Measure the customer's experience

    Probes — an RB750Gr3, for instance — report PPPoE, latency, loss, DNS and jitter over HTTP. Everything is exposed at /metrics for Prometheus and in a ready-made Grafana dashboard.
